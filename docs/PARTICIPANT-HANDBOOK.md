## 1 现在先做什么

你们已经有一条能运行的本地付款链路，今天的两份队友任务也已经发出。接下来先完成这些任务和交接，不再让三个 Agent 各自重新设计项目。MIA 今天负责亲自使用产品、收集交互问题、审阅队友结果和组织集成；不需要在开工前学完所有区块链和 AI 知识。

接下来 90 分钟可以这样安排。

1. 前 15 分钟，确认两位队友的基线 SHA、任务分支、正在验证的问题和预计交接时间。只确认这四项，不临时更换技术栈。
2. 接着 30 分钟，先确认本地 health 就绪、默认 Mock 报价与额度、白名单及执行权限正常、Feed 新鲜且剩余日预算至少 9 美元，再走三笔例子：0.001 ETH 自动付款、0.002 ETH 待 Owner 审批、0.004 ETH 被硬上限拒绝。每笔记下输入、状态、实际到账情况和看不懂的地方；结果不同先记录真实原因，不强行改成示例状态。
3. 最后 45 分钟，把问题交给同一个 MIA 前端 Agent，先完成今天的报价恢复与审批恢复任务。Grok 风格先确定布局，再在这条前端分支继续做；不要另开一个 Agent 同时修改同一份 frontend。

**今天不用等问卷收齐，也不用增加第四人。**当前三人的交接负担已经足够，先做出一段其他开发者可以亲自试用并指出问题的流程。找两位跑过机器人或 Agent 的开发者，各看十分钟：他们最近有没有给运行钱包补 Gas，怎么区分钱包，最怕补错、补重还是预算失控。访谈记录只写真实反馈，不能写成已证明市场需求。

## 2 产品方向怎样收窄

之前的普通转账和给 Agent 钱包补 ETH，确实共用同一条付款能力。仅仅把收款人文案改成 Agent，仍然是自然语言转账；它没有自动形成多 Agent 管理，更没有证明 Agent 已经自主完成工作。

**建议的参赛产品是 Agent Gas 补给助手。**用户维护多个运行钱包，查看真实 ETH 准备金，按用户设定下限和目标提出补给建议，确认后从受约束金库补给。对话表达需求，卡片核对对象和金额，链上规则控制拨款，记录回答“给谁、多少、为何允许或拒绝、是否到账”。当前代码只有受控付款内核，尚未实现这套余额与目标建议。

Gas 场景中分清三项：运行钱包的 ETH 余额、补到目标值需要的 ETH、补款交易自己的手续费。现有 ETH/USD Feed 用于补给金额的美元预算，不是 Gas 费预言机；当前预算不包含补款手续费，也不预测未来任务 Gas 消耗。

这个方向面向已有两个或更多机器人运行钱包的小团队。先解决钱包识别、受控拨款和追踪，首版由用户明确发起。它不要求你们训练模型、托管所有运行钱包私钥、部署多个智能钱包或开发自动资金调度。

建议把下一阶段范围固定成：一个 Owner、一个金库、一个付款执行器、两个可区分的 Agent 运行钱包档案。新增档案管理不是当前已完成功能。先让两个真实不同的地址走通，再决定是否扩展；不要用三个头像配同一个地址来充当多钱包演示。

如果 10 月 19 日之前多档案没有完成端到端验证，就公开说明当前仅支持单个运行钱包拨款，把已验证的受控付款作为交付。缺失能力可以列后续，不要为了讲故事虚构。

**已有并曾通过本地验收的能力：**Node 24 的 TypeScript 后端、viem、SQLite；Owner 挑战签名登录；付款草稿、预览、确认、幂等提交；本地 Solidity 金库；小额自动付款、大额待审批、硬上限拦截；原签名交易恢复；请求哈希和结果事件核对；暗色看板、详情和设置界面。

已有环境为链 31337、真实本地交易和本地 Mock Feed，解析来源为 rule_parser。历史检查点是 19 项合约测试、8 项后端测试和 2 项浏览器测试通过；这不是任意新提交都自动继承的测试结果。当前后台只配置一个 Owner 和一个执行账户，没有真实 LLM 调用，也没有公开测试网完整付款证据。[实现与交接记录](https://github.com/0xChainAegis/aegis-agent/blob/d13493e/docs/HANDOFF.md)

**建议新增但尚未实现的能力：**两个运行钱包档案、明确的档案 ID 与地址绑定、按档案选付款对象、按档案查看拨款历史，以及聊天入口和操作卡片之间的关联。后续模型仅生成草稿，不能取代合约校验。

**暂缓的能力：**自动余额监控、自动触发补款、多个执行 Agent 自主花钱、独立的每 Agent 链上预算、跨链转账、x402 支付 API、图像识别、RAG、EZKL 和模型训练。CRE、CCIP 没有进入当前链路，不因为文章提到就同时接入。

目前的每日预算是整个金库共享的，不是每个 Agent 都有 15 美元。到账运行钱包后的 ETH 也不受本项目后续用途控制，不能保证它只被用于 Gas。

## 4 五种身份要分开

**Owner 是资金主人。**它控制金库策略，在浏览器钱包签名登录，对待审批请求签链上批准或取消。GitHub 的组织 Owner 是代码仓库管理角色，与动用金库资金不是一回事。

**金库是 AegisWallet 合约。**钱先存放在这里，再按规则转出。它不是 Owner 的普通钱包，也不是 Agent 的运行钱包。

**付款执行器是后台配置的 Agent 执行地址。**它替当前产品提交付款请求，自己需要有支付交易 Gas 的测试 ETH。现有 Task.agentAddress 表示这个执行地址，不能直接改成页面选中的运行钱包地址。

**受资助 Agent 的运行钱包是收款地址。**Research Agent、Monitor Agent 可以各有一个运行钱包，接收金库拨款。仅接收 ETH 的钱包不需要因此获得从金库花钱的执行权限，也不需要把私钥交给你们的后台。

**Agent 档案 ID 是应用编号。**它便于选择、显示名称和关联历史，不是一把密钥，也不证明某个人或某个模型真的控制该地址。首版可以由可信 Owner 手工维护地址，明确声明未实现 Agent 地址控制权证明。

最小示例：Owner 管一个金库；执行器提交两类拨款；Research 档案绑定运行钱包 A，Monitor 档案绑定运行钱包 B。A 和 B 是两个不同地址，不是两个不同名字的同一钱包。

合约 ACL 有按地址授权的基础，但当前后端签名器和恢复队列仍为单执行身份。增加第二个自主执行器需要新的认证、签名绑定、nonce 与隔离验证，不能靠加一个 agentId 完成。[当前配置](https://github.com/0xChainAegis/aegis-agent/blob/d13493e/backend/src/config.ts) [钱包权限与预算](https://github.com/0xChainAegis/aegis-agent/blob/d13493e/contracts/contracts/AegisWallet.sol)

## 5 两个 Agent 档案的最小设计

下面是建议契约，供三人下一次同步时确认，不是可以直接调用的现有 API。

- agentId：稳定编号，例如 agent_research_01。改显示名称时编号不变。
- displayName：用户看见的名称，例如 Research Agent。
- chainId：运行钱包所在链；本地演示为 31337，首个公网目标为 Sepolia。
- operatingWalletAddress：真实收款地址；代码与接口可统一采用这个名字，避免与执行器 agentAddress 混淆。
- enabled：是否允许在应用中选择该档案。应用停用仅限制此应用，不能宣称已经链上冻结钱包。
- profileVersion：档案地址等敏感字段变更时递增，旧草稿不能悄悄换收款对象。
- minReserveWei 与 targetReserveWei：用户设定的准备金下限与目标，以 ETH 的最小单位整数记录。实际余额和观察时间来自 RPC，不把样例余额当实时值。

这些字段不包含私钥、API key、模型内部推理或伪造评分。是否要加 description，可以等有明确展示需要时再加。

后台负责从受控 registry 解析 agentId 对应的地址。模型和前端不能自己创造一个同名档案并把它当成已授权钱包。最终付款仍须显示并绑定完整收款地址，合约仍检查 allowlist。档案启用不自动授予链上白名单；链上允许收款也不自动生成应用档案。

建议在付款草稿和历史快照中保留 managedAgentId、managedAgentName、profileVersion 与实际 recipient，旧记录保留当时的地址。现有 agentAddress 继续指执行器。这是待协调的共享 API 增量，由 purple sun 提出 schema、MIA 消费、某齐确认合约含义，不能三人各改一份。

不需要为了首版立即接 ERC 8004、发 NFT 或给每个模型部署钱包合约。如果以后要公开发现或外部 Agent 自助注册，再评估标准身份和地址控制权证明。

## 6 什么才算多钱包功能完成

先写验收，再让 Agent 开发。建议新增能力至少通过这些检查。

1. registry 有两个不同 ID 和两个不同的运行钱包地址。刷新后绑定仍一致，未知或停用的 ID 不能用于生成可付款草稿。
   两个钱包的余额由 RPC 读取并显示观察时间；低于用户准备金下限才建议补给，目标不高于现余额时不建议补给。余额获取失败时不伪造缺 Gas；提交前余额变化使建议过时时要求重新预览。
2. 选择 Research 后，卡片显示 Research、链、完整地址和金额。后台解析出的地址与卡片一致，不能仅靠名称推断。
3. 对 Research 支付一次，本地 Research 钱包实际余额增加，Monitor 钱包不变。再给 Monitor 支付并核对两份独立历史。根据实时共享预算选择测试金额，不把多次测试挤进不足的日额度。
4. 档案改地址后，之前未提交的草稿必须失效或重新确认；已提交的任务仍指向原地址，不能被重写。
5. 修改请求中的 agentId 或 recipient 造成矛盾时拒绝，而不是悄悄选一个字段付款。重复提交和网络超时不产生第二笔拨款。
6. 超过单笔或共享日预算的请求仍被拦截。多个档案不能倍增总预算，Owner 审批也不能绕过硬限制。

达到这些条件，可以说“管理两个 Agent 运行钱包的受控拨款”。它仍不是多 Agent 自主协作、自动补 Gas 或已实现每 Agent 独立硬预算。演示和 README 用同一个表述。

## 7 Grok 风格前端怎么做

借鉴的是对话感和轻量输入，不需要接入 Grok 模型或复制商标。延续现有 Multica 暗色工作台：左侧是钱包档案与操作入口，中间是对话和付款卡片，右侧复用现有详情抽屉。不要另写一套付款状态系统。

首版页面只需要五块：当前 Owner 与环境；Agent 运行钱包选择；对话输入；结构化付款卡片；可打开的真实结果记录。没有多档案数据时仅展示真实可用对象，设计示意里的其他 Agent 明确标成设计稿，不能伪装在线。

交互例子：用户先选 Research，输入“给它补 0.001 ETH”；系统整理出草稿，显示 Research 的完整地址、ETH 数量、美元估值、最高可接受美元成本、报价有效时间和是否需要 Owner 审批。用户确认后提交，再由后端状态更新卡片。

当前规则解析器不理解任意代词或复杂对话。档案解析与真实模型没有完成前，使用明确地址和结构化表单；“给它补”只作为未来交互设计示例。缺字段就补问，不默默填样例地址；歧义金额不自动猜。

对话中的“好的”“完成了”没有资金意义。SUBMITTING 和 BROADCAST 表示处理中，UNKNOWN 表示核对原交易，AWAITING_APPROVAL 表示尚未付款，EXECUTED 才需对应正确执行事件。卡片保留原 taskId，刷新后继续查询同一任务。

付款卡片上的“确认草稿”、连接钱包时的“签名登录”、大额付款时的“Owner 批准并执行”是三种不同操作。按钮文案要解释本次会做什么，不能统统写成 approve。

## 8 Chainlink 在这里解决什么

ETH 数量固定时，美元成本会随 ETH/USD 变化。Chainlink Data Feed 提供价格依据，你们的合约用它检查单笔与共享日预算，并在 Owner 批准时重新检查。它不会帮你训练模型、判断自然语言是否善意，也不代替钱包签名。

本地例子固定 Mock 价格为 3000 美元：0.001 ETH 约 3 美元，0.002 ETH 约 6 美元，0.004 ETH 约 12 美元。配置为 5 美元自动额度、10 美元单笔硬上限、15 美元共享 UTC 日预算。金额用 wei 与 USD6 整数保存；USD6 的 1000000 代表 1 美元。这里没有法币兑换或 USDC 付款。

官方文档说明应用要选择正确网络和 Feed，并通过 updatedAt 等信息判断数据是否足够新。当前 Mock Feed 的结果不能当成公网 Chainlink 实时行情；测试网 Feed、实际部署、真实测试付款要各自留证据。[Chainlink Data Feeds 概览](https://docs.chain.link/data-feeds/overview) [读取 Data Feeds](https://docs.chain.link/data-feeds/using-data-feeds)

你提供的 Sibos 文章有可核对的官方英文版本。它讨论 CCIP 控制能力和 CRE 协调流程，同时保留机构对授权密钥的控制。对本项目的启发是把“提出操作、校验规则、拥有签名权”分清楚；这是我们的设计借鉴，不代表 Aegis 已接 CRE、CCIP、Swift 或银行基础设施。[Chainlink Sibos 2026 官方回顾](https://chain.link/blog/sibos-2026-recap)

申请 Bounty 时重点展示 Feed 缺失、过期或价格变化如何改变付款结果，而不是只在页面放 Chainlink 标签。是否获奖由主办方评审，不能靠接入数量或本文承诺。活动条款以主办方最终发布为准。

## 9 三个人分别学什么和负责什么

**MIA_Ether 负责产品 前端 与集成。**能解释页面上每个状态、完整地址、金额和审批含义；把真实使用卡点转成明确任务；掌握分支、PR 和合并后回归。不需要先成为合约专家。今天继续原前端任务，Grok 风格在同一分支的 P0 之后推进。

**purple sun 负责后端 API 与交易恢复。**维护草稿、任务、幂等、数据库与签名执行；提出 registry 和共享类型方案；证明超时和重启不会重复付款。不要因为会 Go 再迁移现有 TS 服务，也不要把 Owner 私钥放到后端。

**某齐负责可重复验证。**今天继续已经发出的 Oracle 与审批边界测试；算法基础可以用来分析条件、写输入输出样例和模型恶意输出用例，不等于要承担陌生复杂合约的全部安全责任。明天若模型接入启动，可辅助设计严格 JSON 样例和澄清问题，由后端负责人维护适配器。合约授权改动必须让另一人和 Agent 一起复核。

某个任务看不懂时，先让本人 Agent 用“一个输入、一个预期输出、一项断言”解释，再让独立审查 Agent 检查代码细节。你们不需要手写全部代码或通读所有源码；三位参赛者应能解释钱从哪里来、谁能动、什么情况下停止，并亲自复现关键操作。解释和运行结果对不上时先保留分支。

## 10 从队友交付到午夜合并

按团队约定，新的每日分支采用 日期 GitHub账号 项目名称，例如 `2026-10-17-mia03ther-aegis-agent`。其他人用自己的实际 GitHub 账号，不猜账号、不改 Git 作者身份。同一天需要多项独立工作时可加角色或任务后缀。

今天提示词里已有 mia/1016、purple/1016、qi/1016 命名。已开工或已推送的分支继续使用，不为统一外观重写历史；下一个新分支再应用新规范。三个 Agent 不共用同一个工作目录并发切分支。

每人交接七项：分支、完整 commit SHA、改了什么、复现步骤、实际测试命令与结果、未完成项、需要谁接手。让 Agent 输出可复制 PR 正文，但发 PR、评审和合并由本人完成；不要让“AI 说测试了”代替日志结果。

目标分支暂时是 codex/integration-wallet-ui，因为旧 main 缺完整集成。MIA 逐个审阅和合并，不同时合三个共享接口变更。某齐核对后端链上假设，purple sun 核对前端 API 与重试，MIA 核对用户结果和范围；看不懂的关键授权逻辑可另做 Agent 复审。

内部建议在北京时间 22 时 30 分停止加功能，23 时左右收齐交接，午夜前完成可合并项的串行集成和验证。这是工作节奏，不是到点必须合并：失败、缺证据或未读懂的 PR 保留分支，写清阻塞，第二天再处理。

同一个逻辑问题修好并验证后再提交，提交消息解释实际改动。不要求每天固定多少 commit，不回填日期、不改作者、不制造空提交。保留 c3164e6 等已有历史，从现在开始正常迭代即可。

## 11 最小运行与排错手册

所有命令从仓库根运行。先查看 git status、当前分支和 Node 版本；要求 Node 24 及以上。首次按 lockfile 执行 npm ci --ignore-scripts，不要先升级整套依赖。

启动顺序：终端一运行 npm run chain；终端二运行 npm run deploy:local；终端三运行 npm run dev。页面默认 5173，API 3001，RPC 8545。本地测试钱包入口使用明确标识的公开开发账户，只能用于本机 31337 链。收款地址以部署 JSON 或 config 响应为准。

登录失败先核对配置 Owner 和链，Agent 执行地址不是 Owner。页面离线先核对三个服务，不先换模型。等待审批时资金未到账是预期。UNKNOWN 先核对原 taskId 和 txHash，不重建另一笔付款“试一下”。审批失败可能是报价、共享预算、白名单、期限或策略改变，不能统一归因为 AI 不聪明。

重建本地链后使用匹配的新部署和数据库，不拿旧链任务当新证据；保留原证据，不随手删除别人的数据库。运行 npm run test:e2e 时，默认脚本会启动全新链和服务；先辨认 8545、3001、5173 的已有进程，协调测试窗口，不杀队友进程。

日常按改动运行相关检查，集成后由一人执行 npm run check 和 npm run test:e2e。check 包含类型、构建、合约和后端测试，不含浏览器 E2E。前端截图证明界面，余额增量和匹配事件才支持付款结果；夹具 API 测试与真实本地链 E2E 分开写。

当前代码入口：frontend/src/main.ts 管界面，wallet.ts 管钱包交互，backend/src/server.ts 管 HTTP，service.ts 管任务，chain.ts 管链上调用与结果，store.ts 管保存，packages/shared/src/index.ts 管共享类型，contracts/contracts/AegisWallet.sol 和 AegisPriceOracle.sol 管资金与价格校验。先沿一笔付款读这些入口，不必通读所有历史 Python 文件。

## 12 Claude 与现有 Agent 怎么配合

英文协作可以，产品 UI 不必因此全部换英文。对话语言不会改变平台服务地区和账号适用规则；本文不提供规避账号限制的方法，也不把未经核实的国籍说法当平台政策。

产品里的模型接入另开小任务：单 provider、严格 JSON 草稿、超时和歧义处理、地址与金额验证；拒绝模型输出 signer、policy、nonce、calldata 或执行指令。没有真实调用证据就继续显示规则模式。对话流畅程度和资金授权必须分开验证。

## 14 三分钟怎样讲清项目

前 30 秒讲一个待验证的用户问题：我有多个 Agent 运行钱包，需要给它们拨付 ETH，但容易认错对象，也希望付款有预算和可查记录。不要写成已经服务大量客户。

接着演示选 Research、看到地址、输入需求并核对卡片。小额拨款后展示真实本地到账与匹配事件；再换 Monitor 展示独立档案和历史。只有多档案已验收才展示第二个，否则明确首版单钱包范围。

随后演示一笔需要 Owner 的付款，指出尚未到账，再展示 Owner 签名后的结果。最后给出超硬预算或价格失效的拒绝案例，说明安全边界由合约执行。不要为几分钟视频把交易失败或等待改成假成功。

收尾用一句事实说明环境：现在运行于哪条链、价格是否为 Mock、解析来自规则还是真模型、哪些仍未验证。回答评委时由 MIA 讲用户操作，purple sun 讲接口和恢复，某齐讲验证与边界；不会的地方如实说明并指向代码。

## 15 只记住这些编号和词

- agentId 是建议新增的运行钱包档案编号；当前代码尚无该字段。
- agentAddress 在当前任务里是金库付款执行器，不是档案的收款钱包。
- chainId 加地址标识某链的钱包位置；是否有权操作还取决于签名和合约权限。
- draftId 是待确认草稿；taskId 是已提交任务，一名 Agent 可以有很多任务。
- requestHash 绑定固定付款参数，不证明 AI 思考正确；txHash 标识某一笔链上交易。
- receipt 是交易回执；业务 event 才帮助区分入队、执行和取消。回执成功不自动代表已付款。
- nonce 用于顺序和重放约束；幂等用于让同一请求重试时不多做一次。两者不是同一层机制。
- ABI 是代码与合约之间的调用和事件格式；前后端必须用一致版本。
- USD 预算只是 ETH 支出的计价单位，不代表兑换法币或稳定币。

## 16 每次让 Agent 收尾时怎么问

请给我分支与 commit、实际修改文件、解决的用户或安全问题、我可以复现的步骤、每条测试命令和真实结果、未完成项、下一位同学要做什么。请分别写清真实本地链、测试夹具、Mock Feed、真实模型和测试网证据，不用一句“已完成”概括所有层次。

## 17 按 Vibe Coding 方式工作

这本手册按 AI 主力编码来安排，不把你们当成已有多年经验的工程师。写代码、补测试、定位接口、解释 diff 和整理交接，大部分可以由 Agent 执行。三位同学集中处理产品选择、真实操作体验和最终合并。

最小工作循环只有六步：给一项明确任务；让执行 Agent 读当前基线；让它修改并运行检查；把 diff 交给独立审查 Agent；本人照步骤点一遍关键流程；符合验收后推分支并由 MIA 集成。出现失败就把错误原文交回执行 Agent，不需要本人先猜所有技术原因。

MIA 看前端交付，先问“我点哪个按钮、会花多少钱、结果在哪看”。purple sun 看后端交付，先问“重复点或网络断了会不会多做一次”。某齐看测试交付，先问“什么输入必须被拦住，运行时是否真的被拦住”。这些问题能回答，再逐步理解代码原因。

独立审查 Agent 的提示词可以直接这样写：请只读审阅本任务分支相对集成基线的实际 diff，优先找重复付款、权限绕过、金额或地址不一致、假成功、持久化恢复问题。逐项给可复现条件、文件位置和验证办法。已执行检查和未执行检查分开写；不要修改代码，不把作者的完成报告当作自己的证据。若无发现，说明审阅范围和未验证部分。

两位 AI 给出相反意见时，交给集成人看同一个最小复现，不靠谁的语气更有把握。AI 审阅减少遗漏，真实运行验证结果；二者都不能使截图变成转账证据，也不等于正式安全审计。

日常沟通不需要每人先写长报告。七项交接可由 Agent 生成，本人确认与实际一致即可。学习发生在具体问题上：今天知道一个新状态和一种错误，明天能复现它，就足够继续推进。
