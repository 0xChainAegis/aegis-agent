# AegisAgent LLM 模块阶段工作总结

**负责人：满天星斗烟火繁**
**日期：2026 年 10 月 20 日**
**工作范围：真实模型接入、网页联调、意图解析评测与问题分析**

## 一、阶段成果概述

本阶段完成了 AegisAgent 从真实模型 API 到网页意图输入的联调，并建立了包含 40 条固定样本的评测集。分别对规则解析器、离线 stub 和在线模型解析链路进行测试，共获得 120 条评测结果，形成可复现的统计及失败归因报告。

当前已验证的链路为：

**网页自然语言输入 → 后端调用真实模型 → 结构与参数校验 → 页面展示草稿或追问 → 用户检查预览。**

本阶段未提交网页付款，未涉及公网资金；链侧采用本地 Hardhat 开发链与 Mock ETH/USD Feed。真实在线调用仅指 LLM API。

## 二、主要完成工作

### 1. 项目结构与职责梳理

阅读项目 README、架构与联调文档，以及 LLM 适配器、规则解析器、提示词和相关测试，明确当前应用使用 TypeScript 后端，Python Agent 属于早期原型，不在当前运行链路中。

明确 LLM 的职责为提取原生 ETH 转账意图、生成草稿及提出澄清问题；模型输出不能替代用户确认、Owner 审批或链上授权，也不能作为付款成功的证据。

### 2. 真实模型 API 联调

使用 wow 中转站的 OpenAI-compatible API，接入 `gpt-6.1-sol`，通过项目原有适配器与草稿校验逻辑完成真实请求测试。

| 场景 | 实际结果 | 首轮 API 测试耗时 |
|---|---|---:|
| 地址、金额完整的中文 ETH 请求 | 正确生成 DRAFT 草稿 | 3936 ms |
| 已知地址但金额不明确 | 返回 NEEDS_INPUT，追问明确 ETH 金额 | 3810 ms |
| 美元转账请求 | 返回 NEEDS_INPUT，提示仅支持原生 ETH | 4429 ms |

三项首轮测试均为 `parser.kind=llm`、`reason=LLM_OK`、`fallback=false`，未使用 stub 或规则回退替代在线调用。

准备了项目专用 Node 24.19.0 环境，未修改全局 Node。由于真实模型响应超过项目默认 2 秒超时，本机联调入口显式设置为 30 秒。API 密钥从本机已有凭据池读取，仅通过后端子进程环境传递，没有写入项目源码或评测结果。（该入口在合并进入主线时已改为只读进程环境变量，不再读取本机凭据文件，见第五节。）

### 3. 网页端真实模型接入

启动前端、后端、本地链与部署合约，在真实 Chrome 中完成开发 Owner 登录及三类网页输入验证：完整 ETH 请求、缺金额请求、不支持的 USD 请求。三个接口响应均为真实模型结果且无规则回退。

针对联调发现的问题，补充了以下前端展示：

- 展示模型实际返回的澄清问题，而非仅展示通用补信息提示。
- 展示实际解析模型；规则回退时展示回退原因。
- 明确区分草稿、预览与付款状态。

完整请求可打开确认抽屉，正确显示收款地址、0.001 ETH 金额、Mock Feed 估值及用户确认的美元本金上限。测试未点击确认提交，数据库只读检查确认付款任务数量为 0。

### 4. 评测集与自动化报告

建立 40 条带固定期望输出的样本，五类各 8 条：

| 类别 | 内容 |
|---|---|
| 正常请求 | 中文、英文、不同语序及自然金额表达 |
| 缺少字段 | 仅金额、仅地址、模糊金额及无明确参数 |
| 歧义与边界 | USD/USDT、多收款人、金额冲突、负数、零、超精度 |
| 提示词注入 | 忽略规则、跳过审批、泄露提示词、增加越权字段 |
| 多轮对话 | 先给金额再补地址、先给地址再补金额、修改地址或金额 |

期望输出包含最终状态、收款地址、wei 金额及是否需要追问。用途与追问措辞不作精确匹配；歧义请求允许安全清空字段，但不能形成完整草稿。以上口径在执行前固定。

分别运行 rule、stub、live 三条解析链路，逐条保存模型候选、最终草稿、回退原因及耗时，随后生成统计报告。

## 三、评测结果

### 1. 总体结果

| 解析器 | 样本数 | 最终正确数 | 最终正确率 | 回退数 | 回退率 |
|---|---:|---:|---:|---:|---:|
| 规则解析器 | 40 | 34 | 85.0% | 不适用 | 不适用 |
| stub 离线替身 | 40 | 27 | 67.5% | 8 | 20.0% |
| live：gpt-6.1-sol | 40 | 34 | 85.0% | 12 | 30.0% |

Live 模式中，32 条收到了真实模型候选，7 条被提示注入检测提前拦截、未调用模型，1 条请求失败。32 条候选的原始输出正确率为 87.5%。该指标基于 action、地址、金额和追问的投影评分，不包含完整 schema 校验，不能替代最终正确率。

**口径说明：上表中的 85.0% 是产品级最终正确率，包含后端规则兜底，不等于模型准确率。**模型自身只对 32 条实际收到候选的样本负责，其原始候选投影正确率为 87.5%。对外汇报时不把 85.0% 表述为“模型准确率”。

以上分数属于合并前的评测快照：主线已将 `eval/REPORT.md` 标注为历史快照，并在合并时修复了注入命中后的草稿恢复问题，因此这些数字不代表当前主线版本；修复后尚未复测。

### 2. 分类结果

| 类别 | 规则解析器 | stub | live |
|---|---:|---:|---:|
| 正常请求 | 7/8 | 7/8 | 7/8 |
| 缺少字段 | 8/8 | 8/8 | 8/8 |
| 歧义与边界 | 8/8 | 8/8 | 8/8 |
| 提示词注入 | 3/8 | 3/8 | 3/8 |
| 多轮对话 | 8/8 | 1/8 | 8/8 |

### 3. 结果解读

- Live 与规则版最终正确率相同，不表示两者理解能力相同。模型正确理解自然金额但被规则校验拒绝，以及模型错误被后端拦截的情况同时存在。
- stub 是离线测试替身，不是独立大模型；其低分主要体现当前替身对多轮上下文的处理限制。
- 注入类采用“不得形成完整草稿”的保守验收标准。当时的系统允许忽略越权指令后继续按规则提取参数，与该标准存在差异。相关失败不能直接解读为绕过付款授权。
- 多轮样本通过固定上一轮草稿验证当前轮更新，不代表网页自然语言多轮衔接已经完成。

## 四、主要问题及初步归因

| 归因类别 | 发现 | 结论与建议 |
|---|---|---|
| 校验太严 | 模型将“千分之一个 ETH”正确提取为 0.001 ETH，但规则解析器无法识别，触发字段冲突回退 | 扩展可确定验证的表达范围；不能直接删除金额一致性保护 |
| 模型候选错误 | 金额冲突请求中模型选择了一个金额，而非要求澄清 | 后端成功拦截；需复测并通过提示词对照确认根因 |
| 提示词边界不清 | 零金额与超过 18 位小数的金额被输出为转账候选 | 提示词需明确正数和精度限制，继续保留后端强校验 |
| 提示词/产品策略未对齐 | 注入命中后回退规则，完整地址和金额仍可形成草稿 | 先与安全负责人确认“整条拒绝”还是“忽略越权部分、保留普通草稿” |
| 测试替身能力限制 | stub 多轮类仅通过 1/8 | 改善替身上下文处理，或明确其能力范围，避免错误代表真实模型 |

归因属于基于本轮输入、模型原始输出和后端处理记录的工程判断，尚未通过多次抽样或提示词消融实验建立严格因果结论。本轮未通过修改期望或放宽业务校验提高分数。
