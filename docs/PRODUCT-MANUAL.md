# AegisAgent 产品手册

写给参赛团队和第一次了解产品的用户

2026 年 10 月 16 日讨论版。先读懂用户、场景和操作，再决定下一步开发什么。本文提出下一版体验，并明确标注当前做到了哪里。

## 1 我们准备做什么

**建议定位：Agent Gas 补给助手。**你在一个界面查看不同 Agent 运行钱包的 ETH 准备金，按自己设定的下限判断是否需要补给，从一个有美元预算约束的资金池补到目标余额，并查到审批和到账结果。首版由用户确认补给，自动执行后置。

可以把它想成“给自己的链上 AI 小助手补运行所需的 ETH”。这里有两笔不同的钱：补给运行钱包的 ETH 是未来任务的 Gas 准备金；发起补款交易本身也要支付手续费。当前预算限制的是补给金额的美元价值，不是未来任务实际消耗了多少 Gas，补款交易自己的手续费也在该预算之外。

这仍是待验证的产品方向。我们建议先给已经运行过链上机器人或 Agent 的个人开发者使用；他们确实可能有多个运行钱包。普通用户应该看得懂界面，但我们还没有证明完全不懂 Web3 的人有这类日常需求。

**现在已经有：**一个 Owner、一个资金池、一个后台付款执行账户的受控 ETH 支付流程。**建议下一步增加：**两个 Agent 运行钱包档案、真实余额读取、用户设置的下限与目标余额、补给建议、用户确认及历史。现有固定转账流程是补给的付款内核，还不是已经完成的 Gas 管理产品。

“准备金低于下限”来自用户配置，不代表系统已经预测某任务一定缺 Gas。未来任务的真实成本会随交易内容和网络变化；首版不承诺“这笔 ETH 保证运行一周或执行一百次”。

## 2 用一个具体故事理解

以下是用于讨论的场景设想，不是真实客户案例。

小林运行两个链上程序：Research Agent 用一个钱包执行研究相关操作，Monitor Agent 用另一个钱包执行监测相关操作。它们需要 ETH 支付链上操作的手续费。小林通常自己打开钱包，对照地址逐个转钱。

小林想解决的可能是：运行钱包准备金不足使任务中断；地址很像，担心补错；记不清昨天给哪个程序补过；不希望一次多补太多；操作中断时不知道刚才到底有没有付过。先访谈实际开发者，确认哪些问题真的发生、现有钱包为什么不够用。

在建议的 Aegis 体验里，小林选 Research，看见余额低于自己设置的下限，输入“给它补到目标余额”。系统读取真实余额，整理出建议补给量，显示哪个 Agent、完整地址、当前余额、目标余额、补给 ETH、参考美元成本和是否需要审批。确认后，卡片继续显示结果。

如果需要审批，钱仍未付出，必须由小林的钱包签名。如果超出硬预算，即使小林想继续点批准，这次请求也会被拒绝；可以另行调整未来策略，但不能假装原请求本来就合规。

Research 和 Monitor 的名字、余额下限、目标差额、聊天理解和独立档案均属于建议新增。当前演示需要使用真实完整地址和明确转账数量，解析来源仍是规则；没有对应实现前，不宣称已经会按目标余额补给或理解任意聊天。

## 3 建议下一版页面

以下是拟开发体验，当前尚未实现运行钱包档案管理。已有的是暗色看板、输入、付款卡片和详情，不要把设计目标当成已可用功能。

**左侧是我的 Agent。**先只放两个真实档案：Research 和 Monitor。每个名称绑定一个不同运行钱包，显示网络、实际 ETH 余额和用户配置的准备金下限。余额观察时间也应可查。数据尚未接上时，不伪装实时在线。

**中间是对话和操作卡片。**你可以描述需求，也能展开表单补地址与数量。对话负责整理需求，卡片负责核对资金操作；历史卡片保留下来，方便找回同一笔任务。

**右侧是详情。**需要时展开，查看完整地址、报价时间、为什么要审批、交易编号和验证结果。第一次使用的人不必先读开发者文档；技术证明放在可展开的位置。

整体沿用现有 Multica 风格的暗色工作台，聊天入口借鉴 Grok 式的轻量感。这不代表接入 Grok 模型。先把对象、金额和下一步说清楚，再做动画和其他美化。

页面必须让人一眼分清：这是本地测试还是公开测试网，价格是模拟还是真实 Feed，输入由规则还是真模型处理。真实功能与设计示意不能混在一起。

## 4 从打开页面到付款的五步

**第一步 连接自己的钱包。**你是资金池的主人，产品称为 Owner。连接和签名登录是在确认身份，不代表已经付款。当前只有配置好的 Owner 能登录；不是任意用户注册后都能使用的公共钱包平台。

**第二步 选收款对象。**目标版中选择 Agent，查看真实运行钱包及 ETH 余额。低于用户下限时显示“准备金低于设置值”；余额获取失败显示不可判断。当前版仍直接填写完整地址。名称不会自己产生付款权限，不能猜。

**第三步 说需求并核对卡片。**目标版可根据“目标余额减当前余额”建议补给量，当前余额已足够时建议不补。至少核对对象、原余额、目标、补给数量、美元成本及是否审批。提交前余额变化使建议失效时重新预览，不能静默改金额。生成建议和预览本身不付款。

**第四步 确认提交。**小额请求可以由执行账户在预设规则内发起；较大请求进入待审批，由 Owner 再单独签名批准或取消。页面上的草稿确认与钱包里的链上审批不是同一个动作。

**第五步 看最终结果。**付款成功应有匹配的实际到账和执行记录。正在广播、等待审批和结果未知都不能写成已付款。页面中断后优先继续查看原任务，避免又创建一笔“试一下”。

当前界面里策略页主要用于查看，修改策略的完整用户交互尚未交付。用户自助建资金池、维护多个档案等也需要后续开发，不能把这五步当作已经上线的完整公众服务。

## 5 三种典型结果

以下金额只用于本地默认演示：Mock 价格为每 ETH 3000 美元，自动额度 5 美元、单笔硬上限 10 美元、整个资金池每天共享 15 美元；收款地址已允许、执行权限正常、报价新鲜、余额和剩余预算足够。条件不同，以实际预览为准。

这三笔先验证已有付款内核，不证明目标余额监测已经实现。要演示 Gas 准备金不足，需要另外准备真实低余额的隔离测试钱包；默认 Hardhat 账户通常已有大量测试 ETH，不能把高余额钱包硬写成缺 Gas。

**补 0.001 ETH 约 3 美元。**通常在自动额度内。用户先核对卡片再提交，实际执行后才显示已到账。确认之前不会因为聊天里出现“发送”就付款。

**补 0.002 ETH 约 6 美元。**超过自动额度，进入待审批。这时钱没有到账；Owner 签名批准后仍需检查当时价格、预算等条件，也可能失败。Owner 可以取消原请求。

**补 0.004 ETH 约 12 美元。**超过 10 美元单笔硬上限，被规则阻止。这次请求不能靠点击批准绕过限制。

今天已经运行过几笔，可能使剩余日预算不足。不要为了让示例好看去改成功文案或放宽限制。价格变化、报价过期、地址被移出允许名单时，停止付款并解释原因就是正确结果。

## 6 多个 Agent 和多个钱包究竟指什么

**运行钱包档案**可以理解成联系人。Research 有一个编号和收款钱包，Monitor 有另一个编号和另一个收款钱包。编号让界面知道用户选的是谁；它不证明对方是某个真实模型，也不表示它已经完成任务。

**付款执行账户**像资金池的受限操作员。当前系统只有一个，负责提交拨款请求。两个运行钱包都可以是收款对象，不需要因此把它们的私钥交给这个操作员。

因此，建议下一版是“一个资金池给两个 Agent 运行钱包拨款”。这能构成多个运行钱包的管理，但还不是“两个 Agent 都能独立从资金池消费”，也不是“多个 AI 自主协作完成目标”。

真正的多 Agent 自主消费，需要每个执行身份有可靠绑定、权限和独立验证。仅增加一个字符串 ID、头像或模型名称做不到。独立每 Agent 硬预算、自动余额监控和补款暂停恢复，也各有新的开发与测试工作。

运行钱包收到 ETH 后，Aegis 无法保证它只用于手续费。产品控制的是从资金池拨出的这一笔钱，而不是接收钱包之后的所有活动。

## 7 为什么要用 Chainlink

补给数量是 ETH，用户常用美元理解预算。同样 0.001 ETH，在不同价格下代表不同美元价值。Chainlink ETH/USD Data Feed 提供兑换计价依据，合约用它检查本次补给的美元限额，并在审批执行时重新检查。它不直接提供这笔交易的 Gas 报价。

运行钱包 ETH 余额和交易手续费数据来自链上 RPC。补款手续费在交易前只能估算，实际费用以回执为准；它与补给量分开展示。当前产品尚未交付按未来任务预测 Gas 消耗的能力。

它不是给聊天答案盖章，也不代替 Owner 签名。报价不能用时，停止执行比继续按旧价格付钱更符合本产品的目标。参考官方的 [Data Feeds 说明](https://docs.chain.link/data-feeds/overview)。

当前链路用本地 Mock Feed 测试，尚未完成真实公开 Feed 和 Sepolia 付款验证。申请 Chainlink Bounty 的下一步，需要把真实 Feed 的作用与可核查结果做实；不能只增加服务名和图标。

你发的 Sibos 文章强调工作流协调和授权控制的分工。我们借鉴的是“系统整理和校验操作，资金主人保留相应签名权”这件事；没有因此接入银行、Swift、CRE 或 CCIP。[Chainlink 官方回顾](https://chain.link/blog/sibos-2026-recap)

## 8 我们先选择哪种产品

团队可以用三种表述讨论，但最终主演示只选一条。

**方案 A 单钱包受控补款。**输入数量，核对卡片，在预算和审批规则内付款。最贴近现有代码，容易演示；如果没有余额与准备金需求，体验仍接近普通转账。

**方案 B 多 Agent Gas 补给助手。**查看两个运行钱包的 ETH 准备金，对低于用户下限的钱包建议补到目标值，核对美元预算并人工确认。它比固定转账增加了真实余额判断、目标差额、对象与历史管理。建议选这一条，先做用户主动刷新与确认；不承诺自动调度或未来 Gas 预测。

当前系统防止同一请求的网络重试或交易恢复多付一次，不判断两笔独立新建的补款是否重复。查看历史可以帮助用户判断；如果要增加“刚补过，请确认”提醒，应作为单独的新功能。

**方案 C 自动 Gas 补给。**后台持续监测，按阈值触发补给，带冷却、去重、预算、暂停与恢复。它需要新的调度和重复触发防护，可以列后续方向。给多个 Agent 自主消费的独立身份又是另一项扩展，不与这两件事混为一谈。

选择 B 不等于需求已经成立。找两位实际运行过钱包机器人或 Agent 的人，问最近一次补款怎么做、发生过什么错误、会不会用这个工具。对方如果没有困扰，要记录下来，允许调整方向。

面向完全不懂 Web3 的普通消费者，需要先找到他们为什么会拥有一个 Agent 运行钱包。先把界面做得易懂，与已经证明大众市场需求，是两件不同的事。

## 9 读完后你们只讨论这五个问题

1. 谁最可能真正使用：运行多个钱包的个人开发者，还是尚未有明确场景的普通消费者？先选一个，不同时服务所有人。
2. 最值得做的价值是否为“提前看到 Gas 准备金不足，并在预算内安全补给”？对象、历史和审批都围绕这一点，不再各做一个孤立功能。
3. 我们能否在一分钟内解释 Research 和 Monitor 的钱包为什么要收钱？如果只是为了贴 Agent 标签，场景还需要改。
4. 10 月 19 日之前，能否证明两个不同钱包、两份可查历史和统一预算限制？证明不了就缩小表述，不靠假数据补齐。
5. 评委问“你们亲自做了什么”时，能否说明产品选择、AI 生成代码后的验证、真实发现的缺陷和最终演示边界？Vibe Coding 也应保留这些真实工作。

这五个问题由人拍板。之后只给 Agent 一条确定的开发目标。已经分给两位队友的 10 月 16 日恢复与边界测试继续执行，不用因为这份讨论稿半路更换。

## 10 三个人怎样继续推进

MIA 负责用户体验和方向：照本手册点产品、记录卡点、确定聊天与卡片表达，再组织合并。purple sun 负责把草稿、任务、记录和恢复连接起来。某齐负责把“应该允许与应该拒绝”的条件做成可重复验证，也可协助模型输出样例。写代码和查实现细节主要交给 Agent。

每个人完成后交分支、commit、改动说明、可复现步骤、实际测试结果和未完成项。先用独立审查 Agent 帮忙看 diff，再请另一位同学核对改动说明、关键结果与未完成项，作者亲自演示。按日期和账号开新分支，已开工的旧命名分支保留；MIA 午夜前串行合并具备条件的工作，失败项留分支。

今晚你们首先要看到：付款成功是什么样、等待自己审批是什么样、拒绝是什么样。能共同解释这三种结果，再讨论两个运行钱包的新增体验。开发任务和技术细节见 [参赛协作手册](PARTICIPANT-HANDBOOK.md)，它不要求每个人一次读完。

## 13 两篇 Chainlink 文章怎样调整产品

两篇文章的官方版本都已核对。下面的产品取舍是针对本团队的推论，不是 Chainlink 对本项目的背书。

**Sibos 文章给出的启发是授权和协调分开。**它介绍 CRE 协调机构工作流，同时保留机构对授权密钥的控制。映射到 Aegis：用户表达目标，系统检查对象、预算和条件；Owner 保有策略和必要审批的控制。小额执行可以基于预设授权，不要求每笔都手动签，也不能把后台处理直接说成 CRE 已接入。[Sibos 官方回顾](https://chain.link/blog/sibos-2026-recap)

**Vault Adapters 文章给出的启发是资金集中 入口简化。**它让其他网络的资金访问主链上的 DeFi Vault，减少用户手动跨链和切换步骤。映射到产品目标：用户关心“给哪个 Agent 补多少”，后台安排可核对的步骤；先维护一个资金池，避免让每个 Agent 对应一整套新资金系统。[CCIP Vault Adapters 官方介绍](https://chain.link/blog/introducing-ccip-vault-adapters)

这两种 Vault 不能直接画等号。官方适配器面向 ERC 4626 资产和份额的存取；当前 AegisWallet 是原生 ETH 支出金库，没有该标准的份额与存取接口。因此，不能把官方的一键集成描述理解为本仓库直接插上适配器就有跨链功能。[官方适配器说明](https://docs.chain.link/solutions/cross-chain-vault-adapter/reference/adapter-contract)

具体调整是：首版聚焦“发现 Agent Gas 准备金不足，建议补给，按预算确认，追踪到账”，先做两个运行钱包的同链补给；真实 Data Feed 支撑补给金额的美元预算。如果后续用户确实把资金分散在多链，再研究从一条指定来源链补充资金池，需要重新验证支持资产、手续费、异步结果和失败恢复。当前不宣称支持 80 条链。

CRE 可在以后确实需要自动监控和条件编排时评估，CCIP 可在跨链资金需求成立时评估。先完成一个关键 Chainlink 能力的实际作用，再添加有明确理由的下一项。你们今天已经分配的恢复与测试任务仍然有用，保护的就是这条资金流程。
