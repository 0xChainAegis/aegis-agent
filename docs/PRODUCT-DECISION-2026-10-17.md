# AegisAgent 产品决定

2026 年 10 月 17 日。本文确定当前开发主线；已经实现的能力仍以源码和实测为准。Claude 已领取 MIA 的前端 Gas 准备金任务，本轮不另起一个前端实现。

## 产品一句话

**Aegis 帮运行链上 Agent 的个人开发者，发现运行钱包的 ETH 准备金低于自己设置的下限，提出补给建议，在美元预算与审批约束内补 ETH，并查清有没有到账。**

首版用户是已经运行钱包机器人或 Agent 的个人开发者。界面面向第一次接触产品的人，用普通话说明对象、金额、原因和结果。是否适合更广泛的普通消费者，等实际反馈后判断。

## 一次完整使用

以下数字是产品例子，不是当前实时余额或行情。

用户选择 Research 的运行钱包。实际读取余额为 0.0006 ETH，用户设置下限为 0.001 ETH、目标为 0.002 ETH。系统提示低于设置值，建议补 0.0014 ETH。

用户点击准备补给，系统重新读取余额和环境，再通过现有报价流程读取 ETH/USD 和链上限制。假设价格为每 ETH 3000 美元，这次补给本金约 4.20 美元；确认卡片展示最高可接受美元成本。补款交易手续费由发送者另行承担，不计入补给本金预算；当前报价接口没有手续费估计字段，未取得估计时说明“未估算”，不生成假数值。

用户核对对象和金额后确认。通过自动额度的请求由现有执行账户提交；需要 Owner 审批的请求先等待 Owner 单独签名。命中硬预算、白名单、报价或权限限制时停止，页面解释原因。只有匹配的执行事件和付款结果才显示已执行。

这个过程不是“预测还可以运行几天”。下限与目标由用户设置，余额来自 RPC；当前余额与真正执行之间仍可能变化，因此不能保证执行后恰好等于目标值。

## 三个页面足够

**运行钱包。**显示名称、完整地址入口、网络、真实 ETH 余额、观察时间、下限与目标。数据失败显示不可判断，不把失败当零余额。第一轮使用当前配置里的一个真实收款钱包；通过后再扩展为两个档案，不放假在线 Agent。

本轮下限与目标仅保存为当前浏览器的建议偏好，按网络、金库及收款地址隔离，不修改链上美元预算或签名权限。

**补给卡片。**显示收款对象、当前余额、目标余额、实际补给量、美元估值、最高美元成本、报价有效时间、预算与是否需要 Owner。点击准备不会付款，最后确认才提交。建议变化时重新确认，不静默变更金额。

**审批与记录。**复用现有任务卡与详情，显示处理中、待审批、已执行、失败、取消或待核对。保留原 taskId 和交易证据；网络中断后查询原任务，不重新创建一笔付款。

交互延续现有 Multica 暗色工作台，输入可采用 Grok 式的轻量对话感，详情沿用已有抽屉。先使真实动作清楚，再做动画。

## Agent 在哪里

补给助手可以把人的需求整理成草稿，并调用已定义的查询与预览能力。余额差额、金额计算和预算检查采用确定性代码，资金授权由合约和签名决定，模型不能更改权限或直接把请求标成成功。

当前实现是 rule_parser，还没有真实 LLM 调用。将来接模型时，仅允许生成严格校验的草稿；需要真实调用记录才能改宣传。使用 AI 写代码，不等于运行中的产品已经接入 AI。

Research、Monitor 是受服务的运行钱包档案。档案 ID 用于选择和历史，不是一把钥匙。后台现有 agentAddress 是金库的付款执行账户，recipient 才是收到补给的运行钱包。多个收款档案不自动拥有花金库资金的权限，也不等于多 Agent 自主协作。

## Chainlink 做一件关键的事

ETH/USD Feed 将补给本金按美元计价，让合约检查单笔、共享日预算和用户确认的最高成本，并在审批时重查。它不是 Gas 报价源，也不证明模型推理正确。

补款交易本身的 Gas 由交易发送者支付，当前不计入金库的转出本金预算；运行钱包收到 ETH 后的用途也不受本项目继续限制。三个余额要分开：金库余额、执行账户付交易 Gas 的余额、运行钱包准备金。

本地当前仍用 Mock Feed；公开测试网和真实 Feed 需要各自验证。CRE 与 CCIP 保留为需求成立后的扩展，不进入这次已经派发的前端任务。

## 这轮与下一轮

**这轮：**Claude 完成单个真实运行钱包的余额、下限、目标、建议和现有付款流程连接。已有后端、合约 PR 负责恢复与边界证明。集成通过后，三个人能亲自演示一次准备、一次审批与一次拦截。

**下一轮：**purple sun 在同一付款内核上增加两个受控运行钱包档案，提出共享字段契约；MIA 再扩展选择与历史；某齐验证对象不串、地址变更需重新确认、两个档案共享同一金库预算。先完成当前任务，不让 Claude 半途依赖尚不存在的新 API。

第一版不做后台自动监控、冷却调度、每 Agent 独立链上额度、跨链、x402、模型训练或新合约框架。先让一个有用流程完整可查。10 月 19 日根据实际结果决定演示范围，未完成的能力仍标未完成。

## 三个人怎样验收

MIA 看用户能否理解并完成操作；purple sun 看接口、重试和恢复；某齐看余额、事件和硬边界。执行 Agent 给出精确测试结果，另一个审查 Agent 帮忙读 diff，再由另一位同学核对和亲自演示。

不要求每个人手写全部代码，也不要求按天凑提交。每人交真实分支、commit、复现步骤、测试结果和未完成项，MIA 串行合并具备条件的工作。午夜是收尾计划，不是跳过失败检查的理由。
